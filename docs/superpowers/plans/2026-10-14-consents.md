# PDS Consents (v1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A per-project register of consents and their conditions, with server-derived overdue and due-soon indicators and a cross-project "Consents due" page.

**Architecture:**
- A new module, `src/Modules/PDS.Consents`, owns the `consents` table. Contracts holds `ConsentId` and `ConditionId`; everything else is internal.
- The table holds consent items (`PROJECT#pid` / `CONSENT#cid`) and condition items (`PROJECT#pid` / `CONSENT#cid#COND#condId`), with no GSI. The cross-project due list scans the table.
- The module reads projects only through `PDS.Portfolio.Contracts`.
- The web app adds `web/src/features/consents`: a Consents section on the project detail page and a `/consents` page.

**Tech Stack:** Same as the foundation, Risks and Contractors. No new packages.

**Spec:** `docs/superpowers/specs/2026-10-14-consents-design.md`.

**Reference implementations to mirror:**
- Backend: `src/Modules/PDS.Risks` (the closest shape: project-scoped group, store, mapper, close/reopen no-op rule). The `LocalDate` helper pattern is shown below.
- Web: `web/src/features/risks` (section card, modals with a keyed inner component, mutation error helper) and `web/src/features/portfolio/ProjectsPage.tsx` (list page).

## Review Focus

1. **Due-state boundaries** in NZ time, for a condition's due date:
   - yesterday → Overdue
   - today → DueSoon
   - today+30 → DueSoon
   - today+31 → Upcoming
   - completed → Done (even when past due)
   - consent Declined/Withdrawn → None

   For a Granted consent's expiry: today+90 → DueSoon, today+91 → Upcoming, yesterday → Overdue. A non-Granted status → None.
2. **Date-order and status rules:**
   - granted < lodged → 400 on `grantedDate`
   - expiry < granted → 400 on `expiryDate`
   - status Granted without a granted date → 400 on `grantedDate`
   - Completing with a future `completedOn` → 400 on `completedOn`
   - Never 500.
3. **Archived or unknown project.**
   - POST consent or POST condition on an archived project → 400 on `projectId`.
   - Unknown project → 404 on the list and the consent POST.
   - A condition for an unknown consent → 404.
   - Archived projects' items never appear in `GET /api/consents/due`.
4. **Stale edits.**
   - Consent PUT, condition PUT, complete and reopen all return 409 on a stale version.
   - A no-op complete or reopen returns 200 even with a stale version (the Risks close/reopen rule).
   - The UI closes the modal and refreshes on a 409.
5. **Mixed items in one query.** Listing a project's consents must not treat condition items as consents. Group by the `itemType` attribute, and keep a condition whose consent item is missing out of every result rather than crashing.

```csharp
namespace PDS.Consents.Domain;

internal static class ConsentRules
{
    public const int TitleMaxLength = 200;
    public const int AuthorityMaxLength = 200;
    public const int ReferenceMaxLength = 100;
    public const int NotesMaxLength = 4000;
    public const int ConditionReferenceMaxLength = 50;
    public const int ConditionDescriptionMaxLength = 2000;
    public const int ConditionWarningDays = 30;
    public const int ExpiryWarningDays = 90;

    public static bool IsActive(ConsentStatus status) => status is not (ConsentStatus.Declined or ConsentStatus.Withdrawn);

    public static bool IsOrdered(DateOnly? earlier, DateOnly? later) => earlier is null || later is null || later >= earlier;

    public static ConsentFields Normalise(ConsentFields f) => f with
    {
        Title = (f.Title ?? string.Empty).Trim(),
        Authority = Clean(f.Authority),
        Reference = Clean(f.Reference),
        Notes = Clean(f.Notes),
    };

    public static ConditionFields Normalise(ConditionFields f) => f with
    {
        Reference = Clean(f.Reference),
        Description = (f.Description ?? string.Empty).Trim(),
    };

    /// <summary>Guards invariants; the API validators report the same rules as field errors first.</summary>
    public static void EnsureValid(ConsentFields f)
    {
        if (f.Title.Length == 0)
            throw new ArgumentException("Consent title is required.", nameof(f));
        if (f.Status == ConsentStatus.Granted && f.GrantedDate is null)
            throw new ArgumentException("A granted consent needs a granted date.", nameof(f));
        if (!IsOrdered(f.LodgedDate, f.GrantedDate) || !IsOrdered(f.GrantedDate, f.ExpiryDate))
            throw new ArgumentException("Consent dates are out of order.", nameof(f));
    }

    public static void EnsureValid(ConditionFields f)
    {
        if (f.Description.Length == 0)
            throw new ArgumentException("Condition description is required.", nameof(f));
    }

    /// <summary>Done if completed; None if the consent is inactive or there is no due date; else by window.</summary>
    public static DueState ConditionState(Condition condition, bool consentActive, DateOnly today)
    {
        if (condition.CompletedOn is not null)
            return DueState.Done;
        if (!consentActive || condition.Fields.DueDate is not { } due)
            return DueState.None;
        return ByWindow(due, today, ConditionWarningDays);
    }

    /// <summary>Only Granted consents with an expiry date are tracked.</summary>
    public static DueState ExpiryState(Consent consent, DateOnly today) =>
        consent.Fields.Status == ConsentStatus.Granted && consent.Fields.ExpiryDate is { } expiry
            ? ByWindow(expiry, today, ExpiryWarningDays)
            : DueState.None;

    /// <summary>Overdue beats DueSoon; anything else is None (attention only cares about these two).</summary>
    public static DueState Worst(IEnumerable<DueState> states)
    {
        var list = states as ICollection<DueState> ?? states.ToList();
        if (list.Contains(DueState.Overdue))
            return DueState.Overdue;
        return list.Contains(DueState.DueSoon) ? DueState.DueSoon : DueState.None;
    }

    private static DueState ByWindow(DateOnly date, DateOnly today, int warningDays) =>
        date < today ? DueState.Overdue
        : date <= today.AddDays(warningDays) ? DueState.DueSoon
        : DueState.Upcoming;

    private static string? Clean(string? value) => string.IsNullOrWhiteSpace(value) ? null : value.Trim();
}
```

`Features/ConsentValidators.cs`:
```csharp
internal abstract class ConsentInputValidator<T> : AbstractValidator<T> where T : IConsentInput
{
    protected ConsentInputValidator()
    {
        RuleFor(x => x.Type).NotNull().WithMessage("Choose a consent type.").IsInEnum();
        RuleFor(x => x.Title).Cascade(CascadeMode.Stop)
            .NotEmpty().WithMessage("Title is required.")
            .MaximumLength(ConsentRules.TitleMaxLength);
        RuleFor(x => x.Authority).MaximumLength(ConsentRules.AuthorityMaxLength);
        RuleFor(x => x.Reference).MaximumLength(ConsentRules.ReferenceMaxLength);
        RuleFor(x => x.Status).NotNull().WithMessage("Choose a status.").IsInEnum();
        RuleFor(x => x.GrantedDate)
            .NotNull().WithMessage("Enter the date the consent was granted.")
            .When(x => x.Status == ConsentStatus.Granted);
        RuleFor(x => x.GrantedDate)
            .Must((x, granted) => ConsentRules.IsOrdered(x.LodgedDate, granted))
            .WithMessage("The granted date can't be before the lodged date.");
        RuleFor(x => x.ExpiryDate)
            .Must((x, expiry) => ConsentRules.IsOrdered(x.GrantedDate, expiry))
            .WithMessage("The expiry date can't be before the granted date.");
        RuleFor(x => x.Notes).MaximumLength(ConsentRules.NotesMaxLength);
    }
}
internal sealed class CreateConsentValidator : ConsentInputValidator<CreateConsentRequest>;
internal sealed class UpdateConsentValidator : ConsentInputValidator<UpdateConsentRequest>
{
    public UpdateConsentValidator() => RuleFor(x => x.Version).GreaterThan(0);
}
```

Validators:
- Description: NotEmpty ("Describe the condition.") and ≤ 2000.
- Reference: ≤ 50.
- Update: Version > 0.
- Complete: Version > 0, and CompletedOn NotNull ("Enter the completion date.").
- Reopen: Version > 0.

- [ ] **Step 2: Condition endpoints** (in the project group; all CanWrite with `.WithValidation<...>()`).
- **`AddCondition`** — `POST "/{consentId:guid}/conditions"`:
  - Project lookup: unknown → 404; archived → `ProjectArchived()`.

  - `Condition.Create`, then `CreateConditionAsync`.
  - Returns `Created(".../conditions/{id}", ConditionDetails.From(c, consent.IsActive, today))`.
- **`UpdateCondition`** — `PUT "/{consentId:guid}/conditions/{conditionId:guid}"`:
  - `GetAsync` for the consent (needed for `IsActive`) → 404.
  - `GetConditionAsync` → 404.
  - Version mismatch → `VersionConflict("condition")`.
  - Update, then the conditional write (false → 409).
- **`CompleteCondition`** — `POST ".../complete"` (name `CompleteCondition`) and `POST ".../reopen"` (name `ReopenCondition`). Mirror `CloseRisk.Change`:
  - Load → 404.
  - **No-op first** → Ok unchanged.
  - Version check → 409.
  - For complete only: `completedOn > today` → `CompletedInFuture()`. Check this after the no-op check and before applying.
  - Apply, then the conditional write → 409 on failure.

5. Order by Date, then ProjectCode, then ConsentTitle.
6. Return `Ok(List<DueItem>)`.
