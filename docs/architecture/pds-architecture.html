PDS Architecture Set

How the property development system is put together: which AWS services it runs on, how a request travels, how the modules stay apart, and how code gets to production. The first client is a single NZ developer with a small in-house team. The design has to stay cheap and low-maintenance at that size, and be reusable for further clients through a consultancy.

00 · Back of envelope

Sizing drives the shape

This is an internal tool for one company's development team, not a consumer product. Load is tiny, so the main risks are data integrity, ops burden and cost at idle, not throughput. Every choice below follows from these numbers.

Users10–30Staff across Admin, Manager and Viewer roles. Around 5 are active at peak.
Peak load< 5 req/sAt ~200 ms per request that's under one busy Lambda instance.
Data, 5 years< 2 GB100s of projects and 100k-scale cost lines, at ~1–2 KB per item. Documents go to S3 later and will dominate storage.
Idle time~75%Nights and weekends in NZ. Pay-per-use compute costs nothing during them.
Run cost, prod< US$10/moEverything is pay-per-request: Lambda, API Gateway and DynamoDB on-demand. The largest line is likely CloudWatch Logs.
Recovery point≤ 5 minDynamoDB point-in-time recovery, restorable to any second in the last 35 days.
A-01 · Runtime topology

Where a request goes

The browser talks to three front doors: CloudFront for the app, Cognito to sign in, and API Gateway for data. Behind the API sit one Lambda and its DynamoDB tables. There is no network to run: no VPC, no NAT and no connection pool.

A-02 · Request gates

Every way a write can be turned away

Here's what happens to PUT /api/portfolio/projects/{id}. Each gate has one job and one failure code, so the UI can respond precisely: send the user back to sign in, show errors against form fields, or offer to reload a record someone else changed.

A-03 · Module boundaries

One deployable, walls inside

All modules ship together in one Lambda, but each is sealed. C# internal hides everything except a small Contracts/ folder, and each module owns its own DynamoDB table. Risks can ask Portfolio whether a project exists, but they can't see its tables or its classes.

A-04 · Domain map

Project is the hub

All six modules together, as they'll connect once built. Every record traces back to a project. Arrows point from the record that holds the reference to the one it references; a ? marks an optional link. Cashflow is calculated from costs and sales, not stored. Cost totals per category are kept as running-total items written in the same transaction as each cost line.

A-05 · Delivery pipeline

One artifact, promoted

Every change passes one CI gate. The build that passed dev is the exact build promoted to prod, after a person approves it. GitHub signs in to AWS with short-lived OIDC tokens, so no AWS keys are stored anywhere.

A-06 · Tenancy decision

Why each client gets its own account

This decision is the most expensive one to reverse, so here's what was chosen between. Both options serve two clients from one codebase. The difference is whether their data ever shares a table.

Refinements made while drawing this set

  • DynamoDB replaced Aurora PostgreSQL and EF Core (Rev B, ADR-0002). This removes the VPC, the Secrets Manager endpoint, the migrator Lambda and the connection-pool limits.
  • Config comes from CDK as Lambda environment variables, not SSM at runtime.
  • The SPA calls API Gateway directly with CORS. The API address comes from config.json in the bucket, so the same build works for every client.
  • The API uses the Cognito ID token as the bearer token, so it has the email and groups for audit fields without an extra lookup.
